A UI design for a distributed render framework on real Silicon Graphics hardware. The Mandelbrot set is the first compute module, not the point — the shell, the tile scheduler and the cluster panel are meant to outlive it. Nothing is built yet; this is the drawing to argue with.

Callouts

Render window — image only

  1. Tiles land in the owner's colour. A completed tile is drawn immediately; for about 400 ms it keeps a one-pixel outline in the hue of the host that computed it, then the outline fades. You can watch load balancing happen — aurora's tiles outpace lucy's twenty-five to one — without reading a single number. Toggle the outlines off with g for a clean image.
  2. In-flight tiles are dimmed, not blank. The coarse ⅛-scale pass fills the whole frame in well under a second, so there is never an empty canvas; refinement sharpens it tile by tile.
  3. One status line, hideable. Pointer coordinates at full precision on the left, progress and state on the right. F8 hides it for a borderless image. This is the only chrome in this window — the old side panel is gone.
  4. The title bar is a progress display. Magnification and percentage live there, so a minimised or partly covered window still reports. Mouse: drag a rubber-band box to zoom, B2 pans, B3 opens the popup menu (v1 stub: zoom, reset, back/forward, copy coordinates, save image, grid toggle). Keys: + − zoom, arrows pan, Home reset, [ ] history, Space pause, Esc cancel, g grid, F8 status line — and Tab overlays every parameter of the current image at once, stolen shamelessly from Fractint, which got that exactly right in 1990.

Control window — settings above, cluster below

  1. Coordinates are text, at full precision. 17 significant digits, selectable and paste-able, because that is how you return to a view you found last month. The thumbwheel is for hunting, the text field is for keeping.
  2. Colour applies instantly. The GUI keeps the iteration count per pixel, not just RGB, so palette, rotation and smoothing recolour from memory in a frame. No re-render, no cluster involvement. This one decision costs ~1.9 MB per megapixel and pays for itself hourly.
  3. Save is two verbs. Save Image writes what you see. Render to File is a separate, larger job — 4096², supersampled, more iterations — queued to the same cluster.
  4. Start / Pause / Stop, and honest progress. Tiles done, elapsed, ETA and throughput. Pause is real: the scheduler stops handing out tiles and in-flight work is allowed to land.
  5. The host table is the cluster. A checkbox decides participation; the rank count is editable per host; state is a coloured dot with a word next to it. Reachability, RTT and free memory are measured before launch, so an unreachable host is greyed out rather than hanging your job.
  6. The exact mpirun line is visible. The UI writes an Array Services arguments file and runs mpirun -f. Nothing about the launch is hidden, and the file is the saveable cluster profile.
  7. Everything stays scriptable. The arguments file is plain text you can read, edit and run by hand — the GUI is a convenience over the command line, not a replacement for it. That is also how the first milestone gets tested, before any window exists. The log names the transport each host actually got, because with HIPPI on one link and Myrinet on the other, "which wire is this tile on?" is a question you will want answered without guessing.

Why two processes, not one

MPT 1.9 on IRIX cannot spawn ranks at runtime — MPI-2 process management is enabled for Linux partitioned systems only. So the set of hosts is frozen the moment mpirun starts. If the GUI were rank 0, every change to the cluster would kill the windows and lose your view, your zoom history and your log.

So the GUI is its own long-lived process on lucy. It launches the MPI job as a child, talks to rank 0 over a socket, and survives job restarts. Reconfiguring the cluster relaunches the job while the windows stay put. This is also what makes the framework claim credible: a second compute module is a different rank-0 binary and a different parameter table, not a different application.

Rank 0 lives on lucy too, next to the GUI, and computes nothing. That makes the GUI↔master hop a loopback socket, so tile data crosses the network exactly once. Putting the master on aurora would relay every tile twice; running the GUI on aurora and displaying on lucy would push nearly 9 MB per refresh across the wire and lose shared-memory blitting altogether. lucy spends one of its two CPUs on X, the GUI and an idle master, and offers the other to the render — which is the right trade for the machine you are sitting at. 

/* the whole framework contract — a module implements these five */
typedef struct FxModule {
    const char     *name;              /* "mandelbrot" */
    FxParamDesc    *params;            /* drives the settings pane */
    int             npar;
    size_t (*state_size)(void);        /* bytes per pixel of kept result */
    void   (*plan)   (FxJob *, FxTileList *);
    void   (*compute)(const FxJob *, const FxTile *, void *out);
    void   (*shade)  (const void *in, int n, const FxPalette *, unsigned *rgb);
} FxModule;

compute() runs on workers and knows nothing about X. shade() runs in the GUI, which is why palette changes are instant. params is a table, so the settings pane is generated rather than hand-built — the next module gets a UI for free.

The split is enforced at link time rather than by discipline: tess-ui links Xm/Xt/X11 and not libmpi; tess-node links libmpi/pthread and not Motif. If a compute file ever reaches for a widget, the link fails.

Platform conventions this follows

  • appName*sgiMode: TRUE — one resource gets the sculpted IRIX Interactive Desktop look; everything else is stock Motif.
  • Colours and fonts come from SGI scheme symbolic names, never hardcoded — and schemes deliberately exclude rendering areas, which is exactly right for the fractal canvas.
  • SGI's documented pattern for this shape of app is a main primary window plus a support window, which is what these two are; the render window's bottom strip is the documented status area, an XmMainWindow slot rather than an invention.
  • Menu order is SGI's canonical File / Selected / Edit / View / Tools / Options / Help, with Render in the Selected slot and Cluster in Tools — kept in order even though renamed.
  • Focus follows the pointer by default on IRIX, so accelerators are installed per window and the pointer is never warped.
  • SGI's feedback thresholds are numeric: busy pointer at 3 s, a real progress indicator at 5 s. A cluster render is always past both, so the meter is permanent rather than conditional.

Three MPT traps designed around

  • No colons in arguments. mpirun's parser uses : to separate entries, so no generated argument may contain one. Parameters go through the arguments file and a socket, never as colon-bearing argv.
  • stdio cannot carry binary and stdin must be redirected for a backgrounded job — hence a real TCP socket for tiles, with mpirun's stdout reserved for the log pane.
  • MPI_STATS is not a live feed. The environment variable only prints at MPI_Finalize, to stderr. The live counters come from MPI_SGI_stat_get(), which is a different thing with the same name on the tin.

Render lifecycle

idle
→ preflight
→ launching
→ running
⇄ paused
→ draining
→ done
↘ failed

Every message carries an epoch number. Cancelling bumps the epoch, so tiles from the abandoned render are recognised and dropped instead of corrupting the new one — the standard fix for the "stale tile paints over my new zoom" bug, and the reason cancel never has to block. On failure, be honest about what MPT gives you: nothing. MPI_Abort takes down the whole job regardless of which communicator you hand it, and installing MPI_ERRORS_RETURN does not make a dead rank survivable. So the framework's answer is prevention plus speed: preflight every host before launching, time out a tile that never lands, then mark the host failed, drop it from the arguments file, relaunch, and keep the view. A lost node costs you seconds, not your session — which is only true because the GUI is not part of the job.

Build order

Each milestone runs on real hardware and proves one thing. Nothing depends on a later step.

  • 0 · MPT on the boxes. Install mpt, mpi, sma and arraysvcs from the August 2006 Applications CD; one ARRAY block with MACHINE lines, AUTHENTICATION SIMPLE (the installed default is NOREMOTE, which blocks everything), sgi-arrayd 5434/tcp in /etc/services on every node, ~/.rhosts, then arrayd -c -f, ascheck, and finally mpirun host_a,host_b 1 hostname. arrayconfig(1M) will generate and distribute the config for you. Nothing else can be tested until this works.
  • 1 · The build loop. make sgi rsyncs and compiles with MIPSpro over ssh, errors come back to the Mac; make mac builds the same C89 sources against Homebrew Motif and Open MPI for UI iteration.
  • 2 · Two empty windows. Motif 2.1 shell, both top-levels, menus, WM close handling, geometry saved. No compute at all.
  • 3 · Local tiler. The scheduler and the iteration buffer running in-process, single host: tiles appear, palette recolours instantly, save works. The UI is now fully exercised without MPI.
  • 4 · MPI transport. Same scheduler over MPT, one host, several ranks. Prove the socket, the epochs, the cancel path.
  • 5 · Multi-host. Arguments-file generation, preflight, per-host colours, the cluster table live.
  • 6 · Stats and polish. MPI_SGI_stat counters, RTT/bandwidth probes, ETA, log pane, profiles.
  • 7 · Second module. Anything that isn't a fractal, to prove the contract holds. That is the real acceptance test for the framework.

What I need from you

Settled: the name is Tess — a tessera is one tile of a mosaic, which is what the scheduler hands out. 64-bit build (Myrinet's GM library on IRIX ships lib64 and nothing else, so this is forced rather than chosen), one rank per CPU and no threads, 3 bytes per pixel of kept iteration data, Performance Co-Pilot in both directions, a link seam for raw HIPPI later, and X blitting now with GL as a switchable backend.

Aurora is 4 CPUs per brick. Powering all five with the router and the L2 controller costs real electricity, so the everyday state is the main brick alone — 4 CPUs and 4 GB, same hostname, same configuration. Bracketed figures above are the fully-powered shape: 20 CPUs, 20 GB. Cluster totals are therefore 10 CPUs everyday and 26 fully powered. So rank counts are resolved at preflight from the detected CPU count, never stored: one profile covers both shapes, and a stored 20 would silently oversubscribe a 4-CPU aurora fivefold. The panel shows detected against configured, so a half-powered cluster looks half-powered rather than broken.

The everyday shape is also the better development target, not merely the cheaper one: at ten CPUs the three machines contribute roughly 10, 26 and 64 percent, which exercises the load balancer far more usefully than one host doing 89% of everything. The mockup above shows that shape for exactly this reason. Power up the rest for benchmarks and big offline renders — which is what Render to File is for.

Two interconnect facts worth knowing before wiring anything. HIPPI to arthur will be plain TCP — MPT 1.9 removed HIPPI-800 OS bypass entirely, so you keep the bandwidth but not the low-latency path. And which interface the TCP path uses is decided by arrayd.conf's hostname field, not by any MPI variable — so arthur's entry has to name its HIPPI address or the tiles quietly ride ethernet instead. Myrinet to aurora can use real GM bypass, which is exactly what the 64-bit build buys.

The GUI host computes nothing

Lucy has two CPUs and five jobs wanting them: the X server, the GUI's shading and blitting, the master, the PCP collector — and, if you let it, a compute rank. The first four together are a small fraction of one CPU. The fifth pegs one outright for the length of the render.

So the default is zero compute ranks on whichever host runs the GUI. It costs 3–10% of throughput and buys the thing that actually determines how the program feels: a CPU available the moment you drag a zoom box or rotate the palette. Average load is not the metric; latency under load is. A pegged CPU competing with the X server is precisely how a workstation UI comes to feel like treacle, and no throughput figure compensates for a render window that stutters while you are aiming it.

Mechanically: 0 is a legal rank count, and it means something different from unticking the host — an unticked host leaves the array altogether, while a host with 0 ranks stays in the job as master and telemetry source and computes nothing. The table shows mstr only rather than a bare zero, so it reads as a decision instead of an oversight. And it follows the GUI: move the windows to arthur for IR2 work and the default moves with them. Turning it back on is one click, which is worth doing for an unattended overnight render — there is no interactive latency to protect when nobody is watching.

How the shape gets discovered

Three mechanisms at three moments. Preflight uses PCP — a pmFetch of hinv.ncpu, hinv.cpuclock and hinv.physmem per host, which is remote, uniform, needs no agent of ours, and where a context that won't open is simultaneously the reachability answer. Where pmcd is absent, a tiny tess-probe binary runs over arshell and prints one machine-readable line — better than parsing hinv output, whose format varies, and it needs only Array Services, which MPI requires anyway. Then every rank self-reports at MPI_Init, which is authoritative but too late to size the job — its job is to catch the mismatch and say under-subscribed when 4 ranks land on an aurora reporting 20 online CPUs. That is exactly the failure a powered-up aurora invites.

One tess_inventory() function serves all three callers — the probe, the rank hello, and the PMDA — because inventory gathered three ways drifts. And Rescan sits beside Test All, since the shape changes between runs whenever you power bricks up.

Three subsystems the specs added

One rank per CPU — no threads anywhere. Your mandel3.c already showed why: it creates two pthreads and never calls pthread_setconcurrency(), and IRIX pthreads are an M:N implementation that will happily time-slice both workers onto one CPU. It also splits the image into static halves, so even correctly threaded it would show about 1.3× rather than 2× — interior rows cost max_iter per pixel while exterior rows escape immediately. Ranks sidestep both: MPT places processes, MPI_DSM_DISTRIBUTE spreads them across aurora's five bricks, and on one system image all 20 talk over shared memory — faster than the Myrinet link bringing tiles in. It also drops MPT's thread-safety question, and tess-node stops linking -lpthread at all.

Performance Co-Pilot, both directions. Reading: the panel opens a PMAPI context per host and fetches from pmcd, which replaces most of the bespoke stats code with a supported remote API — and a context that won't open is the reachability answer. Writing: a tess PMDA exports the render metrics, so pmchart can plot render rate against CPU and link load on one chart and pmlogger can archive a whole session. The master writes an mmap'd stats file and the PMDA maps it read-only, so pmcd doesn't care when Tess starts or stops, and a stale file reports no values rather than lying. Because the panel and PCP read the same source, they can't disagree.

The link seam. Control always travels on MPI — assignment, epochs, cancel. Only bulk tile payload is eligible for a raw link, MPI carries the handshake that sets one up, and any raw-link failure degrades back to MPI and says so in the log. GM to aurora needs no work because MPT selects it itself; raw hippibp to arthur is a later milestone, gated on measuring TCP-over-HIPPI first. A fast path that can't fail closed isn't worth having.

Three small things to confirm at the machines

None of these block design work, and the preflight probe answers most of them by itself once it runs: what arthur actually is (4×400 MHz and 7 GB doesn't pin the model), aurora's R16000 clock, and lucy's screen resolution — that last one picks the default window layout preset.

The one that could bite: which GM is on lucy and aurora. MPT 1.9's bypass expects SGI's IRIX Myrinet driver 1.0.x, which is the 6.5.13_myrinet_1.0.2.tar already in your Downloads — the community gm-1.6.4 tree is a different lineage. Worth checking with MPI_GM_VERBOSE=1 before counting on bypass.

The name — a woman's name, to match lucy and aurora

Theresa works. A few others that also mean something here, in case one lands better: Tess (a tessera is a single tile in a mosaic — literally what the scheduler hands out), Iris (SGI's own lineage — IRIS, IRIX, the Personal IRIS — and also the aperture you look through), Hedy (Lamarr, who patented frequency-hopping: splitting a signal across many channels), or Grace (Hopper).

My pick is Tess — it is a real name in the same register as lucy and aurora, the mosaic-tile etymology is exactly what the framework does, and it survives the Mandelbrot being replaced by something else. Whatever you choose becomes the binaries (tess-ui, tess-node), the window titles, the X resource class, and ~/.tess/. The resource class has to be the framework rather than the module, or the second application needs its own app-defaults file.

Save formats — my default unless you object

PPM P6 plus SGI .rgb via -limage. PPM is a bare fwrite with no library and no endian question; .rgb is what imgview and ipaste open on the desktop without conversion.

PNG stays a compile-time option rather than a dependency, because prebuilt nekoware libraries may be gcc-built and that is documented as ABI-incompatible with MIPSpro for some struct-returning libc calls.
